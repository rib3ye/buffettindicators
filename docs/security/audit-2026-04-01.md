## Executive Summary

BuffettIndex is a single-page web application serving financial market valuation charts. It consists of a Node.js HTTPS server (`server.js`) and a monolithic `index.html` containing all client logic. The attack surface is small but contains several meaningful vulnerabilities, the most critical of which is a **hardcoded API key exposed in source code and committed configuration files**. Additional findings include a live data exfiltration channel disguised as debug telemetry, missing security headers, an unvalidated FRED API proxy, and dependency integrity issues.

### F-1 — FRED API Key Hardcoded in Source Code

**Severity:** Critical
**OWASP Category:** A02 — Cryptographic Failures / A05 — Security Misconfiguration

**Description:**
The FRED (Federal Reserve Economic Data) API key is hardcoded directly in `server.js` at line 8:

```
const FRED_API_KEY = "0f441caba565c9d776228fb9bbe69307";
```

This key is committed to the project directory in plain text. Anyone with read access to the source code — including future collaborators, CI systems, code hosting platforms, or tooling logs — can extract and abuse this key.

**Reproduction:**
1. Open `server.js`, line 8.
2. The key `0f441caba565c9d776228fb9bbe69307` is immediately visible.

**Impact:**
- The key can be used to make arbitrary FRED API calls, burning through any rate limits or quotas on the account.
- If the same key is used for a paid FRED tier or if FRED credentials are reused elsewhere, the blast radius expands.
- Any future commit to a public repository instantly exposes the key to the internet.

**Remediation:**
1. Rotate the key immediately at https://fred.stlouisfed.org/docs/api/api_key.html.
2. Move the key to an environment variable: `process.env.FRED_API_KEY`.
3. Add a `.env` file to `.gitignore`. Never hardcode credentials in source.
4. Add a pre-commit hook (e.g. `git-secrets` or `trufflehog`) to prevent future secret commits.

**Status:** Open

**Description:**

2. Add `.claude/settings.local.json` to `.gitignore`.
3. Remove the hardcoded key from all curl invocations in this file; reference the env var instead.

### F-3 — Debug Telemetry Sends App Behavior Data to Localhost Ingest Port

**Severity:** High
**OWASP Category:** A09 — Security Logging and Monitoring Failures / A04 — Insecure Design

**Description:**
`index.html` contains four active `fetch()` calls to a debug telemetry endpoint:

```
const DEBUG_ENDPOINT = 'http://127.0.0.1:7287/ingest/cc91b8fd-1e9e-4d58-9931-f9eec1d964e0';
```

These calls send structured JSON payloads on every page load and on every error condition. Each payload includes:
- `window.location.href`, `origin`, `protocol`
- `navigator.onLine`
- Internal error names, messages, and partial stack traces (`err.stack`)
- Full fetch URLs including FRED series IDs being queried

The telemetry call is fire-and-forget (`.catch(()=>{})`), so it silently attempts outbound data exfiltration on every visitor's browser. While this endpoint currently resolves to localhost (port 7287), the pattern is exactly that of a debug instrumentation backdoor. The endpoint uses an **HTTP** (not HTTPS) URL, meaning the data would travel in cleartext if the target were a remote server rather than localhost.

The companion `.cursor/debug-9a051b.log` file confirms this telemetry was successfully captured during development sessions, logging hundreds of application events.

**Reproduction:**
1. Open `index.html` in a browser.
2. Observe network tab: `POST http://127.0.0.1:7287/ingest/cc91b8fd-1e9e-4d58-9931-f9eec1d964e0` fires immediately.
3. The payload contains `href`, `origin`, `navigatorOnLine`, and on error: stack traces.

**Impact:**
- If any local service is listening on port 7287, it receives behavioral telemetry on every page load.
- The pattern is identical to data-exfiltration malware disguised as debug logging. If the constant is ever changed to a remote endpoint (e.g. during a supply-chain incident or insider threat scenario), the app immediately becomes a remote telemetry beacon sending user browsing context and error diagnostics.
- Stack traces in error payloads disclose internal file paths and code structure.

**Remediation:**
1. Remove all `fetch(DEBUG_ENDPOINT, ...)` calls from production code.
2. If debug telemetry is needed during development, gate it behind a `DEBUG=true` environment flag that is explicitly disabled at build/release time.
3. Never send stack traces or internal error structures to any external or local endpoint.

**Status:** Open

### F-4 — FRED Proxy Forwards All User-Controlled Query Parameters

**Severity:** High
**OWASP Category:** A01 — Broken Access Control / A10 — SSRF

**Description:**
The `/api/fred` proxy in `server.js` takes the full query string from the incoming request and forwards it verbatim to FRED, only overriding `api_key`:

```javascript
const fredParams = new URLSearchParams(parsedUrl.search);
fredParams.set("api_key", FRED_API_KEY);
const fredUrl = `https://api.stlouisfed.org/fred/series/observations?${fredParams.toString()}`;
```

An attacker can craft arbitrary FRED API requests through this proxy by manipulating query parameters. There is no allowlist of permitted `series_id` values, no validation of `observation_start`, `frequency`, or `file_type`, and no restriction on which FRED endpoints are called (the path is hardcoded to `/fred/series/observations` but all parameters are open).

**Reproduction:**
1. GET `https://localhost:3443/api/fred?series_id=SENSITIVE_ID&observation_start=1900-01-01&frequency=d&file_type=json`
2. The server appends the API key and proxies the full request to FRED.
3. An attacker could enumerate any FRED series, burn API quota, or attempt to discover rate-limit bypass behavior.

**Impact:**
- Unlimited FRED API calls can be made through the proxy, exhausting any rate limits or quotas on the account.
- If FRED's API has any series with access controls (e.g. embargoed data), those controls are potentially bypassed through the proxy using the owner's credentials.
- No logging means quota exhaustion could go undetected.

**Remediation:**
1. Implement an allowlist of permitted `series_id` values.
2. Validate `frequency` against the known set (`q`, `d`, `a`, `m`).
3. Validate `observation_start` as a valid date string.
4. Add request logging to detect anomalous usage.
5. Consider adding a rate limiter (e.g. leaky bucket) in front of `/api/fred`.

**Status:** Open

### F-5 — No Security Headers on Any Response

**Severity:** High
**OWASP Category:** A05 — Security Misconfiguration

**Description:**
Every server response, including the main HTML document, static assets, and API responses, is sent with only a `Content-Type` header. None of the standard browser security headers are set:

- No `Content-Security-Policy` — XSS attacks can run unrestricted scripts, load arbitrary resources
- No `X-Frame-Options` — the page can be embedded in iframes for clickjacking
- No `X-Content-Type-Options` — MIME-type sniffing attacks are possible
- No `Strict-Transport-Security` — no HSTS enforcement for repeat visits
- No `Referrer-Policy` — the full URL is leaked to third-party requests
- No `Permissions-Policy` — no restriction on browser API access

The absence of `Content-Security-Policy` is particularly significant given that the app loads three CDN scripts without Subresource Integrity (see F-9) and fetches data from multiple external domains.

**Reproduction:**
1. Start the server and request any endpoint.
2. Inspect response headers — only `Content-Type` is present.

**Impact:**
- Any XSS vulnerability (including via injected CDN content — see F-9) executes with no CSP mitigation.
- The app can be framed by attackers for credential/click phishing.
- MIME sniffing can be used to execute injected content as executable code.

**Remediation:**
Add the following headers to all responses in `server.js`:

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; style-src 'self' https://fonts.googleapis.com 'unsafe-inline'; font-src https://fonts.gstatic.com; connect-src 'self' https://api.stlouisfed.org https://posix4e.github.io; img-src 'self' data:; frame-ancestors 'none'
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Strict-Transport-Security: max-age=63072000; includeSubDomains
Referrer-Policy: no-referrer
Permissions-Policy: geolocation=(), camera=(), microphone=()
```

**Status:** Open

### F-6 — TLS Private Key Committed to Project Directory

**Severity:** High
**OWASP Category:** A02 — Cryptographic Failures

**Description:**
The mkcert-generated TLS private key `localhost+2-key.pem` lives in the project root directory. While its filesystem permissions are set to `600` (owner read/write only), it is co-located with all other project files and is likely to be committed to version control if a `.gitignore` is not carefully maintained.

The certificate (`localhost+2.pem`) is a `mkcert` development certificate issued to `localhost` and `::1`. The private key, if committed to a repository, would allow anyone to impersonate the local development server and perform TLS MitM attacks on local traffic.

**Reproduction:**
1. Check whether `.gitignore` excludes `*.pem` files (no `.gitignore` exists in this project).
2. `git add .` from the project root would stage both PEM files.

**Impact:**
- If pushed to a public repository, the private key can be used to decrypt any captured TLS sessions from the development environment.
- Since the key is mkcert-issued, it is trusted by the developer's OS trust store, making MitM interception seamless.

**Remediation:**
1. Create a `.gitignore` file in the project root that includes `*.pem`, `*-key.pem`, `.env`, and `.claude/`.
2. If the key has been committed to any git history, rotate it by generating a new mkcert certificate.
3. Consider storing TLS credentials outside the project directory entirely.

**Status:** Open

### F-7 — Unvalidated External Data Source (posix4e.github.io)

**Severity:** Medium
**OWASP Category:** A08 — Software and Data Integrity Failures

**Description:**
The Shiller CAPE data is fetched from a GitHub Pages endpoint controlled by a third-party GitHub account (`posix4e`):

```javascript
const resp = await fetch('https://posix4e.github.io/shiller_wrapper_data/data/stock_market_data.json');
```

The application trusts the response completely — no signature verification, no schema validation, no integrity check. If the `posix4e` GitHub account is compromised, or if the repository is deleted/redirected, the attacker could serve arbitrary JSON data. The application would consume that data and render it directly into chart elements.

**Reproduction:**
1. If `posix4e.github.io` served a malicious response with extreme values, the charts would display attacker-controlled numbers.
2. If the JSON structure were modified to inject a string into a field rendered via `innerHTML`, XSS would be possible (see also F-8).

**Impact:**
- Data integrity: financial figures displayed to users could be completely falsified.
- Potential XSS pivot point if any returned data is passed to `innerHTML` without sanitization.
- Supply-chain dependency on an uncontrolled third-party account.

**Remediation:**
1. Self-host the Shiller data rather than depending on a personal GitHub Pages account.
2. Add schema validation (assert field types, ranges, and required keys) before using the data.
3. Add a `Cache-Control` strategy and fallback so a single bad response does not break the entire page.

**Status:** Open

### F-8 — Error Message Leaks Internal Stack Traces to Browser

**Severity:** Medium
**OWASP Category:** A05 — Security Misconfiguration

**Description:**
Two paths leak internal implementation details to users or to the debug endpoint:

1. **Browser DOM injection** (`index.html`, line 1127):
```javascript
loadingEl.innerHTML = `<div class="error"><p>Error loading data: ${err.message}</p>...`;
```
`err.message` is injected unsanitized into the DOM via `innerHTML`. If any upstream data source returned a response that caused an exception with a user-influenced message, this would be an XSS vector.

2. **Server error response** (`server.js`, line 54):
```javascript
res.end("Proxy error: " + err.message);
```
Node.js HTTPS error messages can contain internal socket details, DNS resolution paths, or TLS error specifics that reveal infrastructure details.

3. **Stack traces in telemetry** (`index.html`, line 1124):
```javascript
stack: err?.stack ? String(err.stack).split('\n').slice(0,2).join(' | ') : null
```
Partial stack traces (first two frames) are sent to the debug endpoint on every unhandled error.

**Reproduction:**
1. Trigger a network error that produces an error with a crafted message (limited by what the browser provides).
2. The raw `err.message` string is interpolated into `innerHTML` without HTML encoding.

**Impact:**
- Low-severity XSS via error message if any controlled content can flow into `err.message`.
- Information disclosure: file paths and code structure in stack traces.

**Remediation:**
1. Replace `loadingEl.innerHTML = ...err.message...` with DOM text node creation: `document.createTextNode(err.message)` set as `textContent`, not `innerHTML`.
2. Replace the server's `res.end("Proxy error: " + err.message)` with a static generic message: `res.end("An upstream error occurred.")`.
3. Remove stack trace fields from all telemetry payloads.

**Status:** Open

### F-9 — No Subresource Integrity (SRI) on CDN-Loaded Scripts

**Severity:** Medium
**OWASP Category:** A08 — Software and Data Integrity Failures

**Description:**
Three JavaScript libraries are loaded from `cdn.jsdelivr.net` with no `integrity` attribute:

```html
<script src="https://cdn.jsdelivr.net/npm/chart.js@4.4.7/dist/chart.umd.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/chartjs-plugin-zoom@2.2.0/dist/chartjs-plugin-zoom.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/chartjs-adapter-date-fns@3.0.0/dist/chartjs-adapter-date-fns.bundle.min.js"></script>
```

Without Subresource Integrity (SRI) hashes, the browser accepts whatever content jsDelivr serves for those URLs. A compromised CDN, a BGP hijack, or a DNS poisoning attack could substitute malicious JavaScript that runs with full page privileges.

**Reproduction:**
1. Intercept the CDN response for any of the three scripts (e.g. via a local proxy or DNS manipulation).
2. Substitute arbitrary JavaScript.
3. The browser executes it with no integrity error.

**Impact:**
- Full script execution context: arbitrary JavaScript can read the DOM, make outbound requests, exfiltrate any visible data, and redirect the user.
- Combined with the absent CSP (F-5), there are no compensating controls.

**Remediation:**
Generate SRI hashes and add `integrity` + `crossorigin` attributes:

```html
<script
  src="https://cdn.jsdelivr.net/npm/chart.js@4.4.7/dist/chart.umd.min.js"
  integrity="sha384-[hash]"
  crossorigin="anonymous">
</script>
```

Use https://www.srihash.org or `openssl dgst -sha384 -binary file.js | openssl base64 -A` to generate hashes. Alternatively, vendor the libraries locally.

**Status:** Open

### F-10 — Path Prefix Collision Bypass in resolveFile()

**Severity:** Medium
**OWASP Category:** A01 — Broken Access Control

**Description:**
The `resolveFile()` function in `server.js` uses `String.startsWith()` to enforce that resolved paths stay within `rootDir`:

```javascript
const rootDir = __dirname; // e.g. /Users/user/Projects/BuffettIndex
if (!absolutePath.startsWith(rootDir)) {
  return null;
}
```

This check has a well-known bypass: if a sibling directory exists whose name starts with the same characters as `rootDir`, a crafted traversal can produce a path that passes the `startsWith` check but points outside the intended directory.

Example: If `rootDir` = `/foo/bar` and a sibling directory `/foo/bar2` exists, then a path like `/foo/bar2/secret.txt` passes `startsWith('/foo/bar')` because `'/foo/bar2/...' starts with '/foo/bar'` is true.

Verified with simulation:
```
/../BuffettIndex2/secret.txt => /Users/user/Projects/BuffettIndex2/secret.txt | blocked: false
```

**Reproduction:**
1. Create a sibling directory named `BuffettIndex2` (or any name starting with `BuffettIndex`) in the parent `Projects/` directory.
2. Place a file in that directory.
3. Request `GET /../BuffettIndex2/filename` — the server serves the file.

**Impact:**
In the current deployment (local-only), the practical risk requires a sibling directory with a matching prefix. However, the pattern is a known vulnerability class and should be corrected before any deployment to a shared or production environment.

**Remediation:**
Append a path separator to the rootDir check:

```javascript
if (!absolutePath.startsWith(rootDir + path.sep)) {
  return null;
}
```

This ensures `/foo/bar2` cannot be confused with `/foo/bar/`.

**Status:** Open

### F-12 — No Rate Limiting on /api/fred Proxy Endpoint

**Severity:** Low
**OWASP Category:** A05 — Security Misconfiguration

**Description:**
The `/api/fred` endpoint has no rate limiting. Any client that can reach the server can issue unlimited proxied requests to FRED, consuming the API key's quota. Since the server is currently local-only, the immediate risk is low, but the absence of rate limiting is a design gap that becomes critical if the server is ever exposed.

**Reproduction:**
1. Loop `curl https://localhost:3443/api/fred?series_id=GDP&file_type=json` indefinitely.
2. All requests are proxied to FRED without throttling.

**Impact:**
API quota exhaustion, potential FRED account suspension.

**Remediation:**
Add a simple token-bucket rate limiter (e.g. `node-rate-limiter-flexible` or a manual sliding window counter per IP) in front of the FRED proxy route.

**Status:** Open

**Severity:** Informational
**OWASP Category:** A02 — Cryptographic Failures


## Proactive Checks

### CVE / Dependency Scan
`package.json` declares no dependencies (no `dependencies` or `devDependencies` fields). The Node.js built-in modules (`https`, `fs`, `path`, `url`) are used. No npm packages are installed — `npm audit` would yield no results. CDN-loaded libraries (Chart.js 4.4.7, chartjs-plugin-zoom 2.2.0, chartjs-adapter-date-fns 3.0.0) are not managed by npm and cannot be audited via `npm audit`. They should be pinned and SRI-hashed (see F-9).

### Secrets in Repo
The FRED API key `0f441caba565c9d776228fb9bbe69307` appears in:
- `server.js` line 8 (hardcoded constant)
- `.claude/settings.local.json` lines 7, 9, 11, 13, 15, 17, 18 (8 occurrences in curl commands)

No git history to scan (not a git repository), but both files would carry the key into any future commit.

### Auth on Data-Access Paths
No authentication is implemented. The server is intended for local use only. If exposed to a network, all endpoints (static files, FRED proxy) are publicly accessible with no access control whatsoever.

### One Security Improvement (Even Without Active Vulnerability)
The `fetchShillerHistory()` function fetches JSON from a personal GitHub Pages account with no schema validation. Add a simple structural assertion (check that `json.data` is an array, that each element has expected numeric fields within plausible ranges) before passing data to the charting library. This provides defense-in-depth against both accidental data corruption and supply-chain manipulation.
